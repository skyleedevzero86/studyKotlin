# cdc_migration

병원 연구 심의 데이터를 구시스템에서 새 시스템으로 옮기는 과정을 **합성 데이터**로 재현하는 프로젝트 입니다.<br/>
실존 인물·기관·과제와는 관계없습니다.

| 모드     | 내용                                                                                         |
| -------- | -------------------------------------------------------------------------------------------- |
| CSV 이관 | 구시스템 CSV를 올려 스테이징 → 적재 전 검증 → 프로시저 일괄 적재 (수동 일회성 이관)          |
| 첨부파일 | 업로드 한 번에 MinIO 원본 + PostgreSQL `BYTEA` 저장, 구 MinIO 파일 이관                      |
| CDC      | Debezium 초기 스냅샷으로 초기 적재 후, PostgreSQL WAL 변경분을 Kafka로 받아 새 시스템에 반영 |

## 구성

| 구분   | 기술                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------ |
| 백엔드 | Kotlin 2.4, Spring Boot 4.1.2, Gradle Kotlin DSL, Spring MVC, MyBatis XML Mapper, Spring Kafka, Flyway |
| DB     | PostgreSQL 17 두 개: 구시스템, 5441, 새 시스템, 5442                                                   |
| 파일   | MinIO + `attachment_content.file_content BYTEA`                                                        |
| CDC    | Debezium PostgreSQL Connector 3.7.1 , Kafka                                                            |
| 프론트 | Vue 3.5, TypeScript 6, Vite 8                                                                          |
| 테스트 | JUnit 5, PostgreSQL·MinIO·Kafka 실제 컨테이너                                                          |

```
backend/src/main/kotlin/com/sleekydz86/cdcmigration
├── submission   심의 신청·심의 이력
├── migration    CSV 이관, 프로시저 호출, 이관 작업·스냅샷 시작 조건
├── attachment   첨부파일 저장·검증·이관
└── global       설정, 오류, CSV 입력 어댑터, 프로시저 호출 공통, 작업자
```

각 영역은 domain → 포트·서비스 → MyBatis, Kafka, MinIO, Debezium Connect / REST 순서로 의존합니다.<br/>
도메인에는 MyBatis·Kafka·MinIO 타입이 없습니다. <br/>
CSV 읽기와 Kafka 소비는 입력 어댑터이고, MyBatis와 MinIO는 저장 어댑터입니다.

## 실행

```bash
docker compose -f infra/docker-compose.yml up -d
cd backend && ./gradlew bootRun
cd frontend && npm install && npm run dev
```

- 화면: http://localhost:5175 · Swagger: http://localhost:8085/swagger-ui.html · MinIO 콘솔: http://localhost:9101 (minioadmin / minioadmin)
- `minio-init`은 버킷 을 만들고 구시스템 합성 파일을 올린 뒤 **종료 코드 0으로 끝나는 일회성 컨테이너**입니다. <br/>
  `Exited (0)`이 정상입니다.
- 첫 기동 때 Flyway가 `target_db`에 V1~V8을 적용합니다. `legacy_db`는 `infra/legacy-db/*.sql`이 컨테이너 초기화 때 만듭니다.
- npm 설정의 `os` 값이 다르면 `npm install --os=win32 --cpu=x64`처럼 운영체제를 지정해 설치하세요.

## 관리자 실행 순서

### 1. CSV 이관 (성공 · 실패 · 재처리)

1. **이관 실행** 화면에서 "대상 데이터 초기화"를 누릅니다.
2. `sample/csv/`의 `users.csv`, `projects.csv`, `applications.csv`, `reviews.csv`를 골라 "이관 작업 만들기"를 누릅니다.<br/>
   원본 값이 `stg_*` 테이블에 작업 ID와 함께 저장됩니다.
3. **실패 확인:** "다음 실행 한 번 실패시키기"를 누른 뒤 "실행"을 누릅니다. <br/>작업이 **실패**로 남고, 프로시저가 넣은 데이터가 모두 롤백되어 **심의 신청** 화면이 비어 있습니다.
4. **재처리:** 같은 작업의 "재처리"를 누릅니다. <br/>
   **완료 (검증 오류 행 제외)**가 되고 사용자 8, 과제 6, 신청 8, 심의 이력 6건이 들어갑니다.
5. 작업 번호를 눌러 **작업 상세**에서 오류 사유와 최종 검증을 확인합니다. <br/>
   원본 키 기준으로 누락·중복·잘못된 연결이 모두 0건이어야 합니다.
6. **중복 확인:** "재실행"을 누르거나 같은 CSV로 새 작업을 만들어 실행해도 새로 넣은 건수는 0입니다.

신청번호는 8501부터 시작하지만, 실패한 실행이 identity 번호를 먼저 써 버리면 그 다음 번호부터 붙습니다. <br/>
PostgreSQL identity는 롤백해도 번호를 되돌리지 않기 때문이며, 정상 동작입니다.<br/>

### 2. 첨부파일 (일치 · 저장 실패 후 재시도 · 매핑 실패)

1. **심의 신청·첨부파일** 화면에서 신청 하나를 고르고 파일을 올립니다. <br/>
   요청 ID는 자동으로 채워집니다.<br/>
2. "BYTEA·MinIO 비교"를 누르면 DB 본문과 MinIO 원본의 크기·SHA-256이 같다고 나옵니다.
3. **저장 실패:** "다음 DB 본문 저장 실패시키기"를 누르고 다른 파일을 올립니다. <br/>
   오류가 나고 첨부가 **저장 실패**로 남습니다.
4. **복구:** 그 첨부의 "이 요청 ID로 재시도 준비"를 누르고 같은 파일을 다시 올립니다. <br/>
   같은 첨부 ID·같은 객체 키로 **저장 완료**가 됩니다.
5. 같은 요청 ID로 다른 파일을 올리면 **409 충돌**로 거부됩니다.<br/> 10MiB를 넘으면 413입니다.
6. **첨부파일 이관:** `sample/csv/attachments.csv`를 올리면 6건 중 4건이 완료되고 2건이 **신청 매핑 실패**로 목록에 남습니다.

### 3. 초기 적재 · 변경 반영 · 재처리

1. **이관 실행** 화면에서 "대상 데이터 초기화"를 누릅니다. <br/> CDC는 CSV 이관과 따로, 깨끗한 대상 데이터에서 시작합니다.
2. **CDC 반영 현황**에서 "CDC 시작"을 누릅니다. <br/>백엔드가 Debezium 커넥터 를 등록하고, 토픽 접두사 로 초기 스냅샷을 받습니다.
3. "초기 적재 대기 사유"가 사라지고 상태가 **변경분 반영 중**이 될 때까지 기다립니다. <br/>초기 적재는 CSV 이관과 같은 프로시저로 합니다.
4. 구시스템 상태를 바꿉니다.
   ```bash
   bash scripts/legacy-sql.sh -c "UPDATE tb_appl SET status_code = '03', updated_at = now() WHERE inst_code = 'H01' AND regno = '1220'"
   ```
   **심의 신청** 화면에서 H01/1220이 새 신청번호 그대로 **승인**으로 바뀝니다.
5. **심의 이력 선도착:** 신청보다 이력을 먼저 넣습니다.
   ```bash
   bash scripts/legacy-sql.sh -c "INSERT INTO tb_review VALUES ('H01','V-0200','1302','r2001','A','먼저 들어온 이력', now())"
   bash scripts/legacy-sql.sh -c "INSERT INTO tb_appl (inst_code, regno, research_no, applicant_id, title, status_code, submitted_at, updated_at) VALUES ('H01','1302','R-2019-001','u1001','CDC 신규 신청','01', now(), now())"
   ```
   첫 명령 뒤 이벤트가 **재처리 대기**로 남고, 두 번째 명령으로 신청이 반영되면 자동으로 **반영**됩니다.
6. **첨부 이벤트:** 파일 키가 있는 행을 넣으면 첨부파일 이관 작업이 생기고, 파일 복사는 첨부 작업이 맡아 완료 여부를 따로 기록합니다.
   ```bash
   bash scripts/legacy-sql.sh -c "INSERT INTO tb_attach VALUES ('H01','F-1300','1302',1,'신규계획서.txt','text/plain','legacy-attachments','H01/1220/F-1001-plan.txt')"
   ```

## 초기 적재 시작 조건

Debezium의 스냅샷 완료 알림이 왔다고 바로 적재하면 안 됩니다.<br/> 테이블마다 토픽이 따로라서, 알림을 받은 시점에 다른 토픽에는 아직 처리하지 않은 스냅샷 이벤트가 남아 있을 수 있습니다.

그래서 아래 조건이 **모두** 맞을 때만 초기 적재를 시작합니다.

1. 알림 토픽에서 `Initial Snapshot`의 `COMPLETED`를 받았다.
2. 다섯 테이블 모두 알림을 받았고, 알림의 기록했다.
3. 테이블마다 실제로 처리한 스냅샷 이벤트 수가 그 건수와 같다.

확인 방법은 **CDC 반영 현황**의 "초기 적재 대기 사유"와 "테이블별 스냅샷" 표입니다. <br/> 실제 실행에서도 완료 알림을 받은 뒤 "사용자(tb_user) 스냅샷 이벤트 4/9건만 반영됨" 상태로 기다렸다가 시작했습니다.
스냅샷 동안 들어온 변경 이벤트에 `PENDING`으로 보관했다가, 초기 적재가 성공한 뒤 순서대로 반영합니다.

## 중복 수신과 오프셋

- 이벤트마다 테이블·원본 키·LSN 를 만들어 유니크로 저장합니다.<br/> 같은 이벤트를 다시 받으면 만 늘고 반영하지 않습니다.
- 처리 기록과 대상 데이터 변경은 **같은 DB 트랜잭션**에서 커밋하고, 커밋이 끝난 뒤 로 Kafka 오프셋을 확정합니다.
- 신청보다 심의 이력이 먼저 오면 버리지 않고 주기적으로 다시 처리합니다.

## 프로시저

모든 SQL 파일은 Antock 프로젝트 형식의 주석을 갖습니다.

| 프로시저                                                               | 역할                                                                                                                                 |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `sp_validate_migration`                                                | 적재 전 검증: 중복 원본 키, 필수값 누락, 형식 오류, 코드·사용자·과제·신청 매핑 실패, 과제 미연결                                     |
| `sp_apply_migration`                                                   | 사용자 → 과제 → 심의 신청 → 심의 이력 순서로 `INSERT INTO … SELECT …`. 원본 식별자 유니크 + `ON CONFLICT DO NOTHING`으로 재실행 안전 |
| `sp_user_cud`, `sp_project_cud`, `sp_submission_cud`, `sp_review_cud`  | 바자울 형식 등록·수정·삭제                                                                                                           |
| `sp_attachment_cud`, `sp_attachment_content_u`, `sp_file_transfer_cud` | 첨부 메타데이터·BYTEA 본문·이관 작업. READY는 본문이 있어야만 허용                                                                   |

- 프로시저는 MyBatis 매퍼에서 호출하고, 커밋·롤백은 Spring 서비스 트랜잭션이 맡습니다.
- 오류 메시지는 사용자가 이해할수있게 에러메세지를 돌려줍니다.
- 등록·수정·삭제는 작업자·IP·일시를 남깁니다.
- 두 모드의 변환 규칙은 DB 함수 하나를 함께 씁니다.

## 전환 절차 (구시스템 쓰기 중지 후)

1. 구시스템 쓰기를 멈춥니다. 더 이상 변경하지 않습니다.
2. 구시스템의 현재 WAL 위치를 확인합니다.
   ```bash
   bash scripts/legacy-sql.sh -At -c "SELECT pg_current_wal_lsn()"
   ```
3. **CDC 반영 현황**에서 `초기 적재 대기`와 `재처리 대기`가 0건이고, 이벤트 처리 기록의 가장 큰 LSN이 2단계 위치에 이르렀는지 확인합니다. <br/> `재처리 대기`가 남아 있으면 "재처리 대기 지금 처리"를 누르고 사유를 봅니다.
4. 구·신 신청 상태와 심의 이력을 대조합니다.
   ```bash
   bash scripts/cutover-check.sh
   ```
   검증 오류로 제외한 원본 키는 따로 보여주고, 나머지가 모두 같으면 `차이 없음`과 종료 코드 0으로 끝납니다.
5. 차이가 없으면 **CDC 반영 현황**에서 "중지"를 눌러 커넥터를 지웁니다. <br/> 복제 슬롯은 함께 정리됩니다.

```bash
cd backend && ./gradlew test
```

Docker가 필요합니다. 테스트가 PostgreSQL 17, MinIO, Kafka 컨테이너를 직접 띄웁니다.

| 테스트                        | 확인 내용                                                                                                 |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| `CsvMigrationIntegrationTest` | 샘플 CSV 적재 건수, 오류 사유 구분, 재실행 중복 0건, 실패 롤백 후 재처리, ID 매핑                         |
| `AttachmentIntegrationTest`   | MinIO와 BYTEA 내용 일치, 본문 저장 실패 후 같은 요청 ID 복구, 충돌, 상한, 첨부 이관 매핑 실패             |
| `CdcIntegrationTest`          | 다른 토픽 스냅샷 이벤트가 남으면 초기 적재 대기, `접수 → 승인` 반영, 같은 이벤트 재수신, 심의 이력 선도착 |
| 도메인·어댑터 단위 테스트     | 신청 상태 전이, 첨부 저장 상태, 초기 적재 시작 조건, Debezium 메시지 해석, CSV 읽기                       |

Debezium과 같은 형식의 메시지를 Kafka에 직접 보내 소비·오프셋·중복 처리를 확인합니다. <br/> 실제 Debezium 연동은 위 "3. CDC" 순서로 확인합니다.
